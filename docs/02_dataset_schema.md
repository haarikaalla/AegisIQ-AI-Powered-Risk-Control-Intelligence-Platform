# Stage 2: Dataset & Schema Design

All data is **synthetic**, generated by `src/ingestion/generate_data.py` with a fixed random seed
(reproducible). Period: **Sep 2025 – Aug 2026** (12 monthly cycles), business-day granularity
where relevant. Deliberate data-quality issues (nulls, duplicates, out-of-range values,
inconsistent timestamps) and deliberate **control degradations/anomalies** are injected on
purpose — a platform that only ever sees clean, well-behaved data doesn't demonstrate anything
about risk monitoring.

## Why raw transactions, not pre-labeled pass/fail

A common shortcut is to synthesize a "pass_rate" column directly. AegisIQ instead generates the
underlying transactions (trade prices, fee calcs, review dates, etc.) and makes the **Control
Testing Engine** (Stage 4) independently determine pass/fail by re-applying each control's real
test logic. This mirrors what M&T actually re-performs, and lets us later show that the engine
*catches* the injected issues rather than having been told the answer.

## Tables

### 1. `dim_control` — control catalog (21 controls across 6 processes)
| column | type | notes |
|---|---|---|
| control_id | str | e.g. `TC-01` |
| process_id / process_name | str | one of 6 AWM processes |
| control_name | str | |
| control_type | str | Preventive / Detective |
| frequency | str | Daily / Monthly |
| test_procedure | str | plain-language description of the re-performance logic |
| owner | str | synthetic control owner name/role |
| risk_category | str | Operational / Compliance / Valuation / Suitability |
| kri_threshold_pass_rate | float | minimum acceptable pass rate, e.g. 0.98 |

### 2. `trades` (Process 1: Trade Allocation & Execution) — ~15k rows
trade_id, trade_date, account_id, client_segment, security_id, asset_class, side, quantity,
execution_price, benchmark_price, order_block_id, allocation_pct, desk, trader_id,
execution_timestamp, allocation_timestamp

Controls tested: **TC-01** allocation timeliness (allocated ≤30 min after execution), **TC-02**
execution price within 15bps of benchmark, **TC-03** pro-rata allocation fairness within an order
block (±2% of pro-rata share).

### 3. `fee_calculations` (Process 2: Fee Billing) — ~3.6k rows
fee_id, account_id, period, aum, fee_rate, calculated_fee (recomputed), billed_fee (as invoiced),
period_end_date, invoice_date

Controls: **FC-01** billed fee matches recalculated fee within 0.5%, **FC-02** invoice issued
within 10 business days of period end.

### 4. `kyc_cases` (Process 3: Onboarding/KYC-AML Refresh) — ~1.8k rows
case_id, client_id, client_risk_rating, last_review_date, next_due_date,
review_completed_date (nullable = still open), status, documents_complete (bool)

Controls: **KC-01** refresh completed on/before due date, **KC-02** all required documents present
at completion.

### 5. `nav_prices` (Process 4: NAV/Valuation Oversight) — ~5k rows
price_id, fund_id, price_date, price, prior_price, independent_source_price, break_flag (derived),
break_identified_date, break_resolved_date (nullable)

Controls: **NV-01** price variance vs. independent source within 25bps tolerance, **NV-02** breaks
resolved within 3 business days.

### 6. `cash_movements` (Process 5: Cash & Collateral) — ~3.7k rows
movement_id, account_id, movement_type, amount, movement_date, approver_1, approver_2
(nullable = single approval), custodian_match_flag

Controls: **CM-01** dual approval present for movements > $250k, **CM-02** custodian match (no
unresolved break).

### 7. `portfolio_holdings` (Process 6: Suitability & Mandate Compliance) — ~1.5k rows
portfolio_id, client_id, mandate_type, security_id, asset_class, weight_pct, guideline_min_pct,
guideline_max_pct, as_of_date

Controls: **SM-01** portfolio weight within mandate guideline band, **SM-02** suitability review
completed within the required annual cycle (case table `suitability_reviews`).

### Derived / downstream tables (written by later stages, not the generator)
- `fact_control_test_results` — one row per control per test cycle: population, tested, pass,
  fail, exception counts, pass_rate (Stage 4 output).
- `fact_exceptions` — one row per failing transaction with reason code (Stage 4 output).
- `remediation_actions` — tracked actions against open exception clusters (Stage 4/7 output).
- `fact_risk_scores` — composite risk scoring per control per cycle (Stage 5 output).
- `fact_anomalies` — ML-flagged anomalies (Stage 6 output).

## Injected data-quality issues (handled in ingestion/cleaning, Stage 3)
- ~1.5% missing values in optional numeric fields
- ~0.3% duplicate transaction rows (same ID re-extracted)
- A handful of out-of-range values (negative quantities, execution prices of 0)
- Inconsistent timestamp formats in one month of trade data (simulating a source-system change)

## Injected control degradations (the "story" the ML/GenAI layers should find)
- **TC-01** (allocation timeliness): pass rate degrades gradually from ~99% to ~90% over the last
  4 months — a slow drift, not a cliff-edge breach, on purpose (this is what anomaly detection is
  for, vs. a static threshold that only fires once it's already bad).
- **FC-01** (fee recalculation match): a sharp one-month spike in mismatches in Feb 2026 (simulating
  a rate-table change that wasn't propagated correctly) — a step-change anomaly.
- **KC-01** (KYC refresh SLA): a steadily worsening backlog in the last quarter (headcount/volume
  mismatch scenario).
- All other controls perform within normal random variation around their target pass rate, so the
  anomaly detector has to distinguish signal from noise rather than flagging everything.
